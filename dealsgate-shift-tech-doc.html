The problem

A two-party trust asymmetry with
no technical resolution.

Peer-to-peer trade requires the buyer to release funds before receiving goods and the seller to ship before receiving funds. Neither party can move first without incurring uncompensated risk. When the two parties are strangers on Instagram or WhatsApp — with no catalogue, no identity system, and no dispute mechanism — the transaction rationally does not happen.

  • 39M Nigerian MSMEs sell through Instagram, WhatsApp, and TikTok
  • ₦25.85B digital payment fraud loss in 2025 across 67,515 reported cases
  • 80% of Nigerian undergraduates cannot identify basic scam warning signs (SEC)
  • No practical recourse — bank transfers are irreversible; court recovery is impractical for daily amounts
Why existing solutions fail
Escrow-only services protect money but never verify the item. The buyer still receives goods they have never seen.

Inspection-only services verify the item but cannot hold funds. The seller cannot guarantee payment.

Marketplaces require sellers to abandon their own channels — which social sellers refuse.

Neither the money-protection layer nor the goods-protection layer alone closes the asymmetry. They must be coupled — and the coupling must be structural, not procedural.

The technical core

An exhaustive state machine
with a structurally enforced evidence gate.

The protocol defines 14 legal deal states and a closed transition function. Every state change passes through a single verifier that checks the current state against a whitelist of legal next states. Illegal transitions are rejected with HTTP 422 — not by the UI, but by the server, before any database write.

The property
An exhaustive state graph with a closed transition set is a proof of impossibility. If no edge exists from EVIDENCE_REVIEW to LOGISTICS_DISPATCHED except via buyer_approved, then no code path — correct or buggy, client or server — can produce that transition.

Concurrency & integrity

Atomic job assignment.
Idempotent money movement.

Atomic first-accept-wins
Job assignment uses a database-level row lock on the job record. Under concurrent accepts from multiple agents, exactly one transaction can hold the lock. The first commit succeeds; every other is rejected atomically at the storage layer.
SELECT id, status FROM inspection_jobs WHERE id = $1 AND status = 'OPEN' FOR UPDATE;
One active job per agent
A partial unique index on the agent profile enforces the one-job-at-a-time rule at the database level. This constraint cannot be violated by any application bug — it is a property of the schema.
CREATE UNIQUE INDEX one_active_job_per_agent ON vet_agent_profiles (active_job_id) WHERE active_job_id IS NOT NULL;
Idempotent money flows
Every payment, refund, payout, guarantee hold, and wallet transfer carries an idempotency key. Duplicate gateway webhooks return the prior result rather than re-executing. Payment and logistics webhooks are HMAC-verified with a 5-minute replay window.

The invariant

The evidence gate is
the structural guarantee.

The protocol's central invariant is that no legal transition exists from EVIDENCE_REVIEW to LOGISTICS_DISPATCHED except via buyer_approved. That single-edge constraint is what makes the platform a trust protocol rather than an escrow service with additional steps.

  • Escrow custody held by a licensed Nigerian payment partner — DealsGate never holds principal
  • Vet Agent physically inspects the item, GPS-verified within 500 metres of the seller's pin
  • Inspection evidence includes continuous unedited video, IMEI/serial captured on camera
  • Funds release and logistics dispatch are both gated on the same buyer approval
  • All inspection media stored in S3-compatible storage, served only via signed URLs
Transition verifier (pseudocode)
function transition(deal, target): allowed = LEGAL[deal.state] if target not in allowed: raise HTTP_422 if target == "LOGISTICS_DISPATCHED": if deal.state != "APPROVED": raise HTTP_422 # write happens after verification return db.commit(deal.state = target)
Why this matters
Escrow and inspection exist in isolation. Coupling them via a state graph that structurally forbids bypass produces a guarantee neither can deliver alone.

Technical risk

The agent is a Byzantine node.

The failure mode
The evidence gate assumes that continuous video and IMEI-on-camera evidence capture the actual physical item at the actual inspection location. If an agent's device is rooted or jailbroken, the app itself can be modified to inject pre-recorded footage or spoof GPS position. The buyer then approves a report that does not match the item they will receive.

This is not hypothetical. Sideloaded Android APKs are common in Nigeria, and the price of a compromised inspection is bounded by the value of the highest-value item being inspected. The attack has economic incentive.
12-week test plan
Weeks 1–3 · Build mobile capture client with hardware-backed attestation (Android Keystore / iOS Secure Enclave). Every frame signed with device-bound key. Server rejects unverifiable signatures.
Weeks 4–6 · Co-capture accelerometer + gyroscope with each frame. Server stores monotonic timestamp. Injected footage will not match motion profile and cannot be replayed against a later timestamp.
Weeks 7–9 · Structured red-team exercise. Team A attempts frame injection on a rooted device. Team B attempts GPS spoofing via mock location providers.
Weeks 10–12 · Patch every successful bypass, re-run red team, publish the threat model as the security foundation for the production build.
Contingency if attestation fails
Escalate to dual-device signing (seller and agent cross-verify) and mandatory buyer unboxing video stored as Tier-2 evidence. Both controls are already specified in the dispute resolution policy.

Acceptance criteria
1. One end-to-end protected deal executed on production staging.
2. Evidence gate tested against 30 transitions — 14 accepted, 16 rejected.
3. Concurrent accept test — two agents tapping accept within 1 second; exactly one succeeds.
4. Duplicate webhook replay test — payment gateway webhook fires twice; no double-credit.
5. Sandbox escrow integration live against Paystack or Flutterwave API.
